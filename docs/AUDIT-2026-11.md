# Ticha AI audit: security, gaps, offline (November 2026)

Scope: `main` at `2b35478`. Method: read every API route, the proxy (middleware), the Supabase schema, the service worker and the client storage code; ran `npm audit`, `tsc` and `next build`. Then started the production build locally and probed it with curl and Playwright (Pixel 7 emulation, network switched off).

Severity: **Critical** means someone can cost you money or tamper with data today, with no account needed. **High** means a serious weakness that needs one more condition to be exploited. **Medium** means it should be fixed before launch.

---

## Part 1: Security

### C1. No API route checks who is calling (Critical)

None of the 23 route handlers under `src/app/api/` call `supabase.auth.getUser()`. The proxy (`src/proxy.ts`) refreshes the session cookie but never blocks a request. The only gated route is `/api/rag/ingest`.

Verified against the running build, with no cookies and no Origin header:

```
POST /api/tutor/chat              -> reaches the handler (Gemini call)
POST /api/tutor/tts               -> reaches the handler (ElevenLabs call)
POST /api/elevenlabs/signed-url   -> reaches the handler (mints an agent session)
POST /api/ai/quiz                 -> 200
GET  /dashboard, /dashboard/tutor, /dashboard/profile -> 200
```

Impact: anyone who finds the URL can run your Gemini, ElevenLabs and YouTube keys at your expense. `tts` accepts text of any length, and ElevenLabs bills per character, so one script can empty the monthly quota in minutes.

Fix: write one `requireUser()` helper that builds the server Supabase client, calls `getUser()` and returns 401 when there is no user. Call it at the top of every AI, TTS and RAG route. Add a redirect in `updateSession` for `/dashboard/*` when `user` is null.

### C2. The rate limiter doesn't hold (Critical, because of C1)

`src/proxy.ts` keeps counters in a `Map` in memory, keyed on `x-forwarded-for`.

- On Vercel each serverless instance has its own `Map`, and it is wiped on every cold start. The limit is per instance, not per user.
- Against the local build, 70 requests that each sent a different `X-Forwarded-For` value got **0** responses with status 429. The same 70 requests with one fixed value got 10. (Vercel overwrites this header itself, so spoofing it mostly matters if you self-host. The per-instance problem applies everywhere.)
- The limit is one bucket of 60 requests a minute for every route. A Gemini call costs far more than a list of past papers.
- `AGENTS.md` asks for "strict rate limiting per user/device ID on all AI generation routes". That doesn't exist.

Fix: once C1 is done, key the limit on `user.id`. Store the counters somewhere shared (Upstash Redis, or a Supabase table with an RPC). Give AI routes a daily allowance, which is also how the freemium tier gets enforced. Right now the free/pro split in the README isn't enforced anywhere.

### C3. Anyone can edit their own points and streak, so the leaderboard can't be trusted (Critical for gamification)

The `profiles` UPDATE policy is `USING (auth.uid() = id) WITH CHECK (auth.uid() = id)`. It lets a user change every column, including `points`, `streak_count`, `freezes_remaining` and `last_active_date`. The streak is calculated in the browser (`useStreak.ts`) and then written straight to the row. Any student can open the browser console and run:

```js
supabase.from('profiles').update({ points: 999999, streak_count: 365 }).eq('id', myId)
```

Fix: revoke UPDATE on those columns (`REVOKE UPDATE (points, streak_count, freezes_remaining, last_active_date) ON profiles FROM authenticated`). Move streak and point changes into a `SECURITY DEFINER` RPC that works out the result on the server from server time.

### H1. Open redirect in the OAuth callback (High)

`src/app/auth/callback/route.ts` builds the redirect as `` `${origin}${next}` ``, and `next` comes straight from the query string. With `next=@evil.com` the URL becomes `https://ticha.app@evil.com`, which sends the browser to `evil.com`. This is a classic phishing setup: a real Ticha login link that ends on a fake site.

Fix: accept `next` only if it starts with exactly one `/` (`/^\/(?!\/)/`). Otherwise use `/dashboard`.

### H2. The database master key doubles as the admin password (High)

`/api/rag/ingest` authorises a request by comparing the bearer token with `SUPABASE_SECRET_KEY` (the service-role key). So anyone who uploads documents holds the key that bypasses all Row Level Security. Every curl command, shell history and shared Postman collection that contains it becomes a full database leak. The comparison also uses `===`, which isn't constant-time, though that matters little next to the main issue. The route also sends internal error messages back in `details`.

Fix: add an `is_admin` flag (or `app_metadata.role`) and check it with C1's `requireUser()`. Keep the service key for server-to-database calls only.

### H3. Every dependency with a known vulnerability in production (High)

`npm audit --omit=dev` reports 12 vulnerabilities: 1 critical, 10 high, 1 moderate.

- `next@16.2.10` is covered by the critical advisory, which bundles about 18 issues. These include a middleware/proxy bypass with Turbopack (GHSA-6gpp-xcg3-4w24, which matters because this app runs its CSRF check and rate limit in the proxy), several image-optimizer RCEs, and cache poisoning. Upgrade to a version later than 16.4.0.
- `firebase` is in the dependencies but **never imported anywhere in `src/`**. It brings in `@grpc/grpc-js`, which has a high-severity advisory. Remove it.
- Also flagged: `zod`, `postcss`, `sharp`, `nanoid`, `@xmldom/xmldom`. `npm audit fix` resolves most of them.

### M1. Request bodies are never validated or capped (Medium)

`zod` is installed but no API route uses it. `tutor/chat` takes `message`, `history`, `subject` and `performanceScore` from the client as they arrive:
- `history` has no length limit (cost), and the client can include fake `model` turns, which makes prompt injection easier.
- `subject` and `educationLevel` are pasted into the system prompt as-is.

Fix: define a zod schema per route, cap message length (around 2,000 characters) and `history` length (around 20 turns), keep only `user`/`model` roles, and restrict `subject` to an allow-list built from `gceSyllabusData`.

### M2. CSRF check passes when there is no Origin, and trusts all of `*.vercel.app` (Medium)

The check only runs when an `Origin` header is present. It also allows any `*.vercel.app` origin, so anyone's Vercel deployment counts as trusted. Supabase's auth cookies are `SameSite=Lax`, which blocks most cross-site POSTs, so this is a second layer rather than the only one. Still, it should allow your own preview domain pattern, not the whole platform.

### M3. Local data leaks between students on a shared phone (Medium, and very likely in this market)

The app stores more than 25 `ticha_*` keys in `localStorage`, including full name, school, region, struggles, streak dates, notifications and the profile vector. None of them are tied to a user ID, and `signOut()` (`useAuth.ts:110`) clears none of them. In Cameroon a family often shares one phone, so the next student to log in sees the previous student's name, school and streak calendar, and their onboarding gets pre-filled with that data.

Fix: prefix the keys with the user ID, or clear `ticha_*` keys on sign-out.

### M4. CSP allows `'unsafe-eval'` and `'unsafe-inline'` in scripts (Medium)

That cancels most of the XSS protection a CSP is meant to give. The good news: there is no `dangerouslySetInnerHTML` anywhere in `src/`, so React's escaping is doing the real work. Switching to a nonce-based CSP is a hardening step, not urgent.

### What is done well
- Every table has Row Level Security turned on, and the tutor and progress tables are scoped to `auth.uid()` correctly.
- The `SECURITY DEFINER` trigger sets a fixed `search_path`.
- The `past-papers` storage bucket is private.
- Secrets are only read on the server. No `NEXT_PUBLIC_*` variable holds a secret.
- There are no raw-HTML render paths.
- HSTS, nosniff and frame-ancestors headers are present.

## Part 2: What's missing or broken

### Things that look done but don't work
1. **Past paper downloads hand out a random research paper.** `api/papers/[id]/download` tries to sign a URL in the private `past-papers` bucket using the *anon* client. No storage policy allows that, so the signing fails silently. All 28 seed papers have relative paths, so every download falls back to `raw.githubusercontent.com/mozilla/pdf.js/.../compressed.tracemonkey-pldi-09.pdf`, a 2009 paper on JavaScript compilers. The download counter update fails the same way, because there is no UPDATE policy for the anon role.
2. **"Save offline" for videos saves nothing.** `ConceptVideoPlayer.handleSaveOffline` adds the video ID to `localStorage` and shows the "cached" badge. No bytes are stored.
3. **`/api/progress` and `/api/courses` are stubs** that return empty arrays (`// TODO`).
4. **Grounding fails without warning.** `retrieveContext` returns `[]` on any error, and the prompt builder then falls back to "use my general training knowledge". The README promises answers restricted to curriculum material. If embeddings break, every answer becomes ungrounded Gemini and nothing alerts you. Embeddings use `text-embedding-004`, which Google has deprecated, so check the production logs for `[RAG/embeddings]` errors. If it is failing, RAG has been off for a while.
5. **Streaks never reset.** `claimDailyStreak` only adds 1. Nothing breaks a streak after a missed day, except the freeze logic in local storage.
6. **The daily lesson is always requested for A-Level.** `daily-lessons/page.tsx` sends `education: "al"` as a fixed value, whatever the student chose during onboarding.

### Missing completely
- Any automated tests. CI runs `eslint` only, with no `tsc` and no `next build`. Yet the Discord message says "All Linting & Playwright E2E Tests Passed!", which tells the team something that never happened.
- Enforcement of the freemium tier (see C2).
- Server-side records of usage and cost per user.
- An admin interface for loading content. Ingestion is curl only.
- A French translation check. `i18next` is set up, but no check stops untranslated strings from shipping.

### Documentation that's wrong
- The README says "React + Vite + React Router" and "Pure native CSS". The app is Next.js with Tailwind.
- `AGENTS.md` names `@ducanh2912/next-pwa` (Workbox). It isn't installed. The service worker is a hand-written 90-line `public/sw.js`.
- `AGENTS.md` mentions Appwrite and OpenRouter keys. Neither is used.
- `AGENTS copy.md` is a duplicate file.

## Part 3: How well it works offline

**Verdict: the app works a little offline, mostly by accident. It isn't offline-first.**

### What the Playwright test showed (Pixel 7, production build)

| Page (network off) | Result |
|---|---|
| `/dashboard` (visited earlier, after the service worker took control) | Loads from cache. Shows the streak and quick actions. |
| `/dashboard/flashcards` (visited earlier) | Loads. Shows 7 cards built in the browser. |
| `/dashboard/daily-lessons` (visited earlier) | Page shell loads, then **"NO LESSON AVAILABLE · RETRY"** |
| `/past-papers`, `/dashboard/tutor`, `/dashboard/subjects`, `/summaries` (not visited) | **`net::ERR_FAILED`**: the browser's own offline error page |
| Any offline banner or message anywhere | **None**. The code never checks `navigator.onLine` |

### Why

1. **The service worker only registers on `/dashboard`.** `PWAInstaller` is mounted only in `dashboard/page.tsx`, so visiting the landing page or the login page registers nothing (confirmed: no caches after the landing page loads).
2. **The first visit is never saved.** The service worker installs during the first dashboard visit but doesn't control that page yet, so its HTML isn't cached. Reloading `/dashboard` offline right after a student's first visit fails (confirmed). Only pages visited *after* that are cached.
3. **The fallback page is never cached.** When a navigation fails, the service worker falls back to `caches.match("/")`, but `/` is never put in the cache. The result is `respondWith(undefined)`, which the browser shows as its own error page.
4. **Nothing is pre-cached except two avatar images.** The page shells, the offline page and the syllabus data are all missing from the cache.
5. **API responses are never cached**, and the service worker skips every `/api/` request. Past paper lists, summaries and lessons all need the network.
6. **The daily lesson is saved but never read back.** `daily-lessons/page.tsx` writes `ticha_today_lesson_data` after a fetch, but when the page loads it always fetches again. The saved copy is only read by the flashcards page.
7. **The cache only grows.** Every `/_next/static` chunk ever downloaded stays under `ticha-pwa-v3` until someone manually bumps the version name, and there is no size limit. That is wasted storage on low-end phones. It costs no extra data, though, because the chunks have already been downloaded.

### The real gap is in the design

The README's pitch is "students can download daily modules and interact with cached materials completely offline". The features that create value (lesson, tutor, quiz, flashcards, summaries) all generate content **on demand** from Gemini. No service worker setting fixes that, because you can't cache an answer nobody has generated yet. Real offline support means **generating ahead of time and syncing**:

- When the student is online (or on Wi-Fi), download a **daily pack**: tomorrow's lesson, the quiz, flashcards and summaries for their subjects. Store it as JSON in IndexedDB. Generate each pack once per subject, topic and level on the server and share it across students. That also cuts Gemini costs a lot.
- Past papers: **"Download for offline"** saves the PDF in Cache Storage. This needs download bug 1 fixed first.
- Quiz answers, streak claims and progress get **queued in IndexedDB** and sent when the phone is back online (Background Sync, with a fallback on the `online` event).
- The tutor stays online-only, but it should *tell* the student that and point them to their saved pack.

Smallest useful fix, about a day of work: register the service worker in the root layout, pre-cache an `/offline` page and the main page shells, read the saved daily lesson before fetching, and add a `useOnlineStatus()` hook with a banner. The daily pack is the real feature, and it deserves its own plan in `prompts/`.
